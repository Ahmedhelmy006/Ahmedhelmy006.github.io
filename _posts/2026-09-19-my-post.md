### The Problem

Imagine with me the amount of data that can be produced by a trading application backoffice.Complex relationship between the buyers and the different parties involved, money settlement operations, and most importantly, rapidly changing stock prices. And you need all this data to feed to Analytics for different functions, machine learning operations and a distributed system that feeds user data to a fleet of agents.

### The Context

If you’re not a data engineer, here is a hint. The standard practice for data movement across different data sources usually happens in two ways. Either you do an initial load and stream changes with producer-consumer setup, or you have an UpdatedAt column at your table to move batches from. 

Usually, you need a set of pointers on the changes happening so you only move the changes \- [Read about CDC](https://www.databricks.com/blog/what-is-change-data-capture). My situation was far more complicated. No pointers, no CDCs, no stable updated at column. Nothing, just a very limited read access to a certain database. 

Resources? A conservative warehouse service budget \-, and  VM that is running a fleet of spark operations doing the backend data applications. And access to spotify premium (I pay for it)

And we want the data to be updated every two hours, and 0.5% error rate ( I always aim for 100% anyway, my reconcilers are telling me so). 

### Functional Requirements: 

- The trading system produces valuable data that can help shape business decisions, and train ML Models. So it must belong to the company’s single source of truth: The warehouse.   
- There is no possibility of not being accurate. Everyone’s finances are at stake here.   
- Optimally, the data is needed real-time, but a one hour micro batches is enough for now. 

### Non-Functional Requirements: 

- Scalable. Very. If the size is 30GB in the beta phase, in a year this size is expected to at least triple.   
- The Tech ops can not provide a data stream from their end. 

### Decisions Before the Architecture:

- Because the operations performed on the database will \-lowkey- be select \* from the entire database, this must be far away from the production database main engine. That's why we needed to connect to standby database yet synced with the prod. *There was a complete story behind this, but I can't share it due to technical restrictions.*
- Network Bandwidth. Originally, our cloud enterprise was capped at XB/s bandwidth, so I hopped on a call with the cloud architect to increase this XB/S.   
- VM Specs increase. Because we are still using a Pyspark instead of having a dedicated spark cluster, we needed an increase CPU and RAM to double down, as the current server specs can sometimes struggle with existing jobs. 

Going through this process, I realized that being a senior engineer does not mean that you only deal with code. Sure, that’s maybe 80% of what I do. But there is 20% in knowing the capacity of your team, the teams you interact with, and knowing how to talk to the right people. It’s also knowing how far your solution will sustain. Knowing that you should proceed with plan B immediately after Plan A is deployed.

### The Implementation Plan:

#### 1- The Core Idea: Row Hashing.

In data engineering, hashing is the fallback approach to CDC. It’s where you know that every unique row produces a unique hash. That’s how I decided to proceed.

#### 2- The Primary Bottleneck: Fucking up your Upstream:

The whole idea of CDC is not to overwhelm the production database. The engine was never meant to serve you \- the data engineer, it was meant to serve the production. Since you don’t have any pointers, you have to take the same data over and over again. The more the data grows the more work the engine need to do alongside its primary job. 

And though this is a replica of an active active database setup in the second node. I am very far from the production. Yet, this is not how it’s meant to be done. 

#### 3- The Bright Side: Full Control Over the Downstream:

Now, here is where I get to optimize for the warehouse’s budget. Where I get to optimize for my own servers and processors. Where I can make use of Parquet’s compression (according to my calculation it’s 85:1 ratio). Where I can surgically modify my current tables at nearly no mentionable extra budget. Where I also get to use my codebase’s originally built functionalities. Helpers, Readers, Writers, Exceptions and Configs. 

### The Implementation:

![Architecture of the snapshot load](/assets/diagram.png)

#### 1- The Metadata Reader

This one is a bit simple. It asks the upstream database: What tables do you have? What’s the size of each? Was any new table added? Any removed? Who is this table’s primary key? It’s your average CRUD operation collecting info and updating the metadata database, which tells the pipeline what to do. It writes the information to the job metadata. It also includes some hand picked tables that should not move

#### 2- The Planner:

This is what takes over after the Metadata Reader is over. Decides the plan: What will move? Given the configs, how many partitions per table? And how many workers will be spinned? Per table and per the entire job?

#### 3- The Connection Budget:

This one acts as a semaphor. Ensuring that thrashing never occurs. A class designed to be the controller that permits workers to acquire jobs and demands the resource release. 

#### 4- The Camera:

The camera’s job is to receive the plan, fetch the table given the instructions in the plan, take a snapshot of the table, and then hashes the row, producing a unique combination of the row hash and the primary key. The table is then written to a parquet file on the server’s disk via a docker mount. 

When the writing is successful, the camera writes the table’s data to the manifest. Its schema fingerprint (to handle schema drifts if they occur), the table’s path to the server’s disk, the time taken from start to finish, the number of partitions applied, and the estimated count of the rows. All of which is written to the pipeline database so the rest of the modules pick up from here.

#### 5- The Snapshot Index :

The decider. It doesn’t do anything beyond taking the manifest output and decides if it will use one of three modes: Diff, Full-Reload, and Skip. The Full-Reload is an edge case that we’ll talk about later. It was also further optimized to cut down the time from 2+ minutes to 1:50 seconds. The Skip happens when no change happens to the table, we simply find out no hash changes. So we lowkey skip it.

With every table, it writes the decision for this table, so the writer knows what to do with this table.

How does it make the decision? It simply compares the two newest written files to each other and find out the difference between the two. 

#### 6- The Differ:

This one Takes the tables with the Diff mode, and finds out exactly what changed. Inserted rows IDs are written in the change log and marked as “I”. And the Updates labeled as “U”s. And the deletes are labeled as “D”s. 

This happens by comparing the two newest *written* tables to each other. The differ also has a rule: If the diff is higher than a certain given ratio *\- now sets at 0.5 \-* the full reload is much cheaper.

#### 7- The Writer:

This one takes the “I”s and inserts them, takes the “U”s and updates them, and the “D”s and deletes them per each table to the destination database. Giving us a mirror from the upstream database to the downstream database which lives in the data warehouse.

### What Didn’t Work and How I Handled it (in order):

1- The Row Hash abstract concept did actually work. What didn’t work was using the row hash only. My original idea is that we sort ascendingly sort the table by its ID and detect hashes drifts. The only issue with this approach: Vulnerability to tables with no primary keys.   
   
Sorting them becomes distracted, it’s hard to tell apart the insertions and updates using only the row hash. Thus the combination of primary key \+ row hash was added, Now it’s easier to tell updates from deletes from insertions. 

2- The initial setup was a controller-planner setup.  *(which later turned to become the connection budget \- Planner setup).* The key idea was having multiple spark sessions to achieve true parallelism.  

This was very VERY expensive in terms of resource handling. Multiple spark JVMs with all their networking dependencies. The controller uses state management to handle each Process() state using an SQL Lite state management database. All processes report back to the controller via terminal messages (which freezes all terminal usage if it’s not in a docker sandbox). 

Not only was this over engineering, it scales terribly, deadlocks are more prone. 

The solution was to use a shared spark session and let it consume all the CPU resources with simple Threading management. Less thrashing, easier to manage and achieved faster performance

3 \- Applying Full Reload to the tables with no primary keys. Remember in issue \#1 when we mentioned using a combination of primary key \+ row hash. Some tables do not have a primary key in their DDL. That’s when I introduced the *pk\_inferred* flag. Because we can’t know for a fact if the combination is unique, I did a full reload for this table (After all, data integrity is the \#1 requirement, at all costs). 

The solution was then broken into two steps instead of one (blind full reload). The first step is to produce a table hash for the entire tables whose *pk\_inferred* flag is set to true. If the latest two files produce the same hash, the snapshot index marks the table’s ingestion mode to *SKIP,* which did cut down the time from \~2:30 (mm:ss) to \~1:30 (mm:ss).

### Reflecting:

While this approach is acceptable across most of its components. The only unacceptable pattern is what the camera does to the database engine. 

It’s not truly scalable. Yet, since we're not directly hitting the prod, chances of causing any bottlenecks has drasitcally been reduced. 

That’s why I started plan B immediately, which is using a true CDC \+ Debezium for handpicked tables that are essential for the data operations. 

Plan A will remain. It can be run once as an after night job. Only if we CDC’ed the tables we need.
